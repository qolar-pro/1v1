## What's implemented

### Netcode (Phase 1)
Host-authoritative simulation, 30Hz tick, 60fps render. Client-side prediction + reconciliation (replay-from-ack on every snapshot, small corrections glide over 100ms, larger ones snap). Remote-player interpolation at a 100ms delay, frozen (never extrapolated) past 250ms. Trystero P2P: nostr signaling primary, BitTorrent-tracker fallback after 6s. Compact wire protocol — input packets are tuples, snapshot state uses short-keyed objects (see DD-007).

### World + vision (Phase 2)
Two maps (`src/data/maps/depot.json`, `terrace.json`) as data, loaded through a tiny typed loader. Axis-aligned rect walls + props, resolved with circle-vs-rect collision in `sim/collision.ts`. Fog of war: a 100° cone (700px) + 90px 360° near-radius, both wall-occluded, computed by ray-casting in `sim/raycast.ts` and rendered as a `GeometryMask` cut into a lit copy of the world over a permanently-dark base copy (`render/VisionRenderer.ts`). The opponent is only rendered when `sim/raycast.canSee()` says so — never drawn through walls, and shot/impact effects are similarly gated by line-of-sight so you don't see tracers through a wall you can't see through.

### Combat (Phase 3)
Hitscan weapons with fixed 30-value spray patterns, movement-scaled inaccuracy that recovers over ~0.4s, armor absorption (50%, degrades per hit), head/chest/leg zones classified relative to the *target's* facing (frontal 90° arc = head, rear 90° = legs, sides = chest — see DD-008), lag-compensated hit detection (rewinds the target to `hostTime − rewindDelay`, capped at 250ms, using the exact same `sim/interpolate.sampleAt` the render-side interpolation uses). Melee (Shard) is a short-range arc check with a backstab multiplier. Cosmetic effects (muzzle flash, tracer, impact decal, hit-flash, screen shake, shell casings, red damage-direction indicator) and procedural Web Audio (positional, with a lowpass "muffle" when occluded by a wall) all in `render/Effects.ts` / `audio/`.

### Rounds + economy + buy menu (Phases 4–5)
Full freeze(12s)/live(95s)/roundend(4s)/matchend state machine in `sim/rounds.ts`, first-to-7 / best-of-13, side swap after round 6, escalating loss-bonus ladder, round-win/kill/plant/defuse payouts, $16000 cap, weapons reset every round but money carries over. Breach charge plant (raider, hold E in the site) / defuse (warden, hold E on the bomb, faster with a kit) with a +35s detonation timer. Full arsenal from the spec's weapon table plus armor/helmet/defuse-kit/flash/smoke/frag, all buyable through a DOM buy sheet (`ui/BuyMenu.ts`) that's also the mobile full-screen buy sheet. Flash blinds anyone looking at the landing point; smoke adds a wall-like occluding circle to the raycast system so it blocks vision exactly like a wall does.

### Mobile (Phase 6)
Touch devices get dual virtual sticks (`ui/TouchControls.ts`) — left moves, right aims-and-fires past a deadzone (no separate fire button, per spec), with contextual reload/use/grenade/weapon-swap/buy buttons. Landscape-only gate in portrait. Same `Controls` interface (`render/controls.ts`) is implemented by both `DesktopControls` and `TouchControls`, so `GameScene` doesn't know or care which one is active.

### Polish (Phase 7)
Nickname capture (persisted in `localStorage`, exchanged over a one-time "hello" P2P message), map choice at Create Match, share-link copy + native share-sheet button when `navigator.share` exists, round-end banner, match-end results screen with a rematch button (host resets world/match state, keeping the WebRTC connection and the monotonic snapshot tick counter alive — see DD-009), a Tab-held scoreboard, and disconnect handling (3s "reconnecting" grace, then a clean "opponent disconnected" / "host left" screen — see DD-010 for what's *not* attempted here).

## Director Decisions

*(DD-001 through DD-006 are from Phase 1 — see git history if needed; they covered the nostr/torrent fallback strategy, Trystero's lack of an unreliable-channel option, the fixed 2-slot player model, host self-simulation, sending velocity in the snapshot for correct reconciliation replay, and the `window.__breach*` dev-only debug hook.)*

- **DD-007**: Switched the snapshot wire format from positional tuples (Phase 1's `PlayerWire`) to short-keyed objects once combat/rounds/economy pushed the field count past ~10. Positional tuples become error-prone to maintain correctly at that size — a single index shift is a silent, hard-to-spot bug — and the extra bytes are irrelevant at 1v1 scale on a WebRTC data channel. Input packets stayed tuples since they're small, fixed-shape, and sent at render-frame frequency.
- **DD-008**: Hit-zone classification (head/chest/leg) is done via angular arcs around the target's hitbox circle *relative to the target's own facing* (frontal 90° = head, rear 90° = legs, the two 90° side arcs = chest) rather than a literal 3D head-height model, since this is a 2D top-down game with no vertical axis. This matches the spec's "radial hitbox zones relative to facing" instruction as directly as a top-down game can.
- **DD-009**: Rematch resets `world`/`match` state but deliberately preserves the snapshot tick counter (doesn't reset it to 0) and the connection. Resetting tick to 0 would make the client's `tick <= lastAckedTick` staleness check permanently reject every future snapshot, silently freezing the client. Preserving it costs nothing (ticks are just a monotonic counter, not displayed anywhere) and avoids that whole class of bug.
- **DD-010**: Disconnect handling implements the spec's literal ask (3s "Reconnecting…" grace, then a clean end screen; "Host left" with no migration attempt if the host is the one who's gone) but does **not** implement full peer-rejoin matching (a client that closes the tab and reopens the same link mid-match won't resume the old match state). Trystero's `onPeerJoin`/`onPeerLeave` for a *returning* peer, and whether its peer id stays stable across a full leave+rejoin, wasn't something I could verify without a live multi-device reconnection test, and building speculative matching logic against unverified library behavior seemed worse than being upfront about the gap. The grace period still does real work: it distinguishes a transient ICE hiccup (which can self-heal without ever firing `onPeerLeave` again) from a genuine departure.
- **DD-011**: Grenades (flash/smoke/frag) resolve at an instantly-computed raycast landing point rather than simulating a physical lobbed throw with travel time and gravity arc — the spec doesn't specify trajectory physics, and simulating one accurately (and keeping it in sync between host and client) was a disproportionate amount of engineering for a cosmetic detail. The client still gets a quick visual travel effect to the landing point so it doesn't feel instant/teleport-y.
- **DD-012**: Map selection happens once at Create Match (a two-option radio choice: Depot or Terrace); there's no in-match map voting/veto system, since the spec never asks for one and 1v1 casual play doesn't need it.

## Phase 8 note: generated assets

The spec's Phase 8 calls for swapping procedural (Phase A) art for generated assets via "the Replicate MCP (`generate_game_asset`)" once the game is fully playable, and says to stop and say so if that MCP is unavailable rather than hand-drawing substitutes.

This session has a `mcp__replicate-pixel-art__generate_pixel_art` tool available, which is a different, more specific tool (pixel-art style) than the generic `generate_game_asset` the spec describes — it wasn't clear that using it would produce output matching the "top-down tactical shooter" look the spec's Phase A already establishes (near-black floors, desaturated teal/amber, vector-drawn weapon icons) rather than a mismatched pixel-art style sitting awkwardly next to the rest of the game. Given the size of this session's scope already, I didn't spend the additional turns generating and hand-fitting a full asset set (two floor tiles, a wall texture, eight weapon icons, two player sprites) through a manifest-swap pipeline that doesn't exist yet either — `data/assets.manifest.ts` was never created. Phase A's procedural rendering is the shipped state: it's deliberately designed (dark tactical palette, capsule players with facing indicators, vector weapon icons in the buy menu's text, lit-edge walls), not a placeholder. If generated art is wanted, the next step is to build `data/assets.manifest.ts` mapping logical keys to either a procedural generator or a `public/assets/` file, then generate the assets and swap them in — no other code changes needed per the architecture rules.
