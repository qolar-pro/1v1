## The 3D pivot

The original spec (and Phases 1–7 below) built a **top-down** tactical shooter: Phaser 2D renderer, a 2D vision-cone raycast rendered as a fog-of-war mask, mouse-aim toward the cursor. Partway through the session the user asked for **full 3D first-person** instead. That's not a camera swap — it's a different rendering engine, a different camera/input model, and a fundamentally different answer to "how does vision work."

**What was replaced:**
- Phaser (2D-only) → **Three.js** (WebGL, real 3D). `render/Scene3D.ts` replaces the old `render/GameScene.ts`; `render/VisionRenderer.ts` (the 2D fog-of-war mask) was deleted entirely.
- Top-down mouse-aim (`aimAngle` = angle from player to cursor) → **pointer-lock mouse-look** (`aimAngle` = camera yaw, accumulated from `mousemove.movementX/Y`). `render/DesktopControls.ts` and `ui/TouchControls.ts` were rewritten for FPS-style input (WASD relative to camera facing, not world axes; mobile got a dedicated FIRE button since "aim" is now always screen-center, not a directional stick).
- The 2D vision-cone fog-of-war mask → **real 3D occlusion**. Walls and props are now actual extruded 3D geometry (`WALL_HEIGHT`/`PROP_HEIGHT` in `config.ts`), so the opponent is hidden behind them by ordinary WebGL depth-testing — no synthetic masking needed at all. `sim/raycast.ts`'s `canSee`/`hasLineOfSight` are still used, but only for what they were always *actually* deciding: audio occlusion (wall-muffled sound) and whether to spawn cosmetic muzzle-flash/tracer/impact effects, not for hiding the opponent's mesh.

**What did *not* change, because the coordinate system was kept deliberately compatible:** `sim/` (movement, collision, combat, rounds, economy, grenades), `net/` (host/client sessions, wire protocol), and the entire round/economy/buy-menu/scoreboard/results UI layer. Sim coordinates `(x, y)` map directly to Three.js `(x, z)` with a fixed height axis; pitch (looking up/down) is a client-only visual value that never reaches the sim — hitscan is still a flat horizontal ray at `EYE_HEIGHT`, exactly like the original top-down design, which is *why* none of `sim/combat.ts` needed to change. This was the single biggest lever in keeping the pivot tractable: only the render + input layers were rewritten.

**A real bug this pivot surfaced and fixed:** several full-screen DOM overlays (`#buy-menu`, `#connection-status`, `#match-end`) set `display: flex` via an ID selector, which — being higher-specificity than the browser's default `[hidden] { display: none }` — silently won, leaving those overlays covering (and click-intercepting) the *entire screen*, invisibly, at all times once the game started, even while "hidden." This didn't block the old Phaser build because Phaser's pointer tracking listened at the document level regardless of click target; it completely blocked the new pointer-lock-on-click flow (the canvas's own `click` listener never fired, because the invisible overlay was always the real hit-test target). Fixed with one rule (`[hidden] { display: none !important; }` in `styles.css`) rather than patching each overlay — see DD-013.

## Director Decisions — the 3D pivot

- **DD-013**: `[hidden] { display: none !important; }` added globally in `styles.css` rather than patched per-overlay — see the bug description above. One rule protects every current and future `hidden`-toggled element in the app.
- **DD-014 (superseded — see "round 2" above)**: Originally, pitch was visual-only and hitscan stayed a flat ray at `EYE_HEIGHT`. This broke player expectations ("bullets don't go where the crosshair looks") badly enough to be reported immediately, so it was revisited: pitch now travels per-input (not persisted state) and feeds a proper vertical hit check, without needing the full rewrite this entry originally worried about — the horizontal (XZ) wall-blocking raycast, lag compensation, and spray-pattern system are all untouched; only the *player-hitbox* check gained a vertical component. Kept here as a record of the original tradeoff and why it didn't hold up.
- **DD-015**: Mobile input dropped the original top-down spec's explicit "twin-stick, don't use a separate fire button" guidance in favor of a dedicated FIRE button. That guidance was written for a top-down game where the right stick doubled as both aim direction and a fire trigger; in first-person, aim is always screen-center (camera-driven), so there's no "push the stick toward what you want to shoot" gesture left to repurpose — every mobile FPS (COD Mobile, PUBG Mobile, etc.) uses left-stick-move / drag-to-look / dedicated-fire-button for exactly this reason.
- **DD-016**: Remote-player visibility gating (the old `canSee()`-based check deciding whether to *render* the opponent) was removed outright rather than kept as a redundant safety net. Real WebGL depth-testing against actual wall/prop geometry already produces correct occlusion; keeping a parallel 2D check would either duplicate that behavior (harmless but pointless) or, worse, disagree with it at floor/ceiling edge cases and no longer have a clear "which one wins" answer. `hasLineOfSight` is kept for effects/audio gating, which is a different, still-valid question ("should this sound be muffled / should this muzzle flash spawn") from "is the opponent mesh visible" (which 3D rendering answers by itself now).
- **DD-017**: Smoke grenades render as a translucent grey sphere at the landing point (added after initially shipping the pivot with no visual for smoke at all — caught in review). It's not a true volumetric/particle effect and doesn't itself block the renderer's depth test (the underlying hitscan raycast in `sim/raycast.ts` still treats it as a proper occluding circle for bullets, unchanged from the top-down build) — a reasonable approximation given the time budget, not a gap in the actual gameplay-relevant occlusion logic.
- **DD-018**: No shadow mapping. Muzzle-flash `PointLight`s and the camera-attached "headlamp" light don't cast shadows (Three.js shadow maps are a real perf cost, and occlusion for *audio/effects* is already handled correctly by the raycast system regardless of whether the lighting itself is shadowed). This means light can technically bleed through a thin wall visually in extreme cases; the tradeoff was judged acceptable for a 1v1 game where the counterparty is a human, not a shadow-exploiting adversary the way lighting bugs matter in a hardened competitive shooter.
- **DD-019**: Walls stay full-height blockers for the vertical-aim fix rather than getting true 3D raycasting — the horizontal (XZ) wall/segment raycast is unchanged, and only the *player hitbox* check gained a vertical dimension. A shot that would technically clear a 240-unit wall by pitching up steeply enough still gets blocked. Given `MAX_PITCH` caps looking up/down at ~85°, the maps' walls are much taller than the ~75-unit player hitbox, and no map has any elevated geometry to shoot over, this approximation doesn't cost anything a player could actually exploit.
- **DD-020**: A jumping player's `jumpZ` is *not* rewound alongside x/y/angle in lag compensation (`hostHistory`/`joinerHistory` only ever tracked those three fields). The vertical hit check uses the target's *current* `jumpZ`, not a historical one. Jump arcs are ~0.8s and the rewind window is capped at 250ms, so the practical error is small, and extending the lag-comp history buffers to a fourth field for a fast-decaying edge case wasn't worth the churn.
- **DD-021**: `jumpVel` isn't included in the wire protocol or in the client's reconciliation merge (only `jumpZ` is synced). After a snapshot reconciles the client's predicted `jumpZ` to the authoritative value, the client's own stale predicted `jumpVel` continues integrating from there. This self-corrects within a frame or two (gravity integration converges quickly, and position corrections under 2px already glide rather than snap), so it wasn't worth widening `PlayerWire` for.

## Post-pivot fixes and additions (round 4): player model + visual cohesion pass

Reported by the user: "everything looks out of place" — asked for the player model and general graphics cohesion to be fixed, missing/bad ones first.

- **Player model rebuilt from boxes, not a capsule.** The old model was a `CapsuleGeometry` body with a flat white `ConeGeometry` glued on as a facing indicator — a smooth, undetailed placeholder that clashed hard against the sharp-edged box/wall/crate/gun geometry everywhere else in the scene, which is exactly what read as "out of place." The new `buildPlayerMesh()` assembles a low-poly soldier from the same box-primitive language as the rest of the scene: legs, torso, two arm/sleeve blocks, a head, and a small emissive visor slit (team-colored, replacing the cone as the facing cue). A gunmetal-textured chest plate sits on the torso — deliberately reusing the same texture the weapon viewmodels use, so the player model, guns, and environment now visibly share a material family instead of each looking independently generated.
- **Found and fixed a real texture mismatch, not just a geometry one**: the crate prop texture (`crate_wood.png`, generated in the prior round) came out as warm olive-green wood, while every other surface in the scene (floor, walls, gunmetal) is a cool dark blue-grey steel palette. Sitting a wood crate in an all-steel corridor was a real, visible clash — likely a good chunk of "looks out of place" on its own. Regenerated as `crate_steel.png` (dark riveted gunmetal crate, matching palette) and swapped it in via the manifest; the old file was deleted rather than left unused.
- **Gun grips textured instead of flat-colored.** The grip material on every weapon viewmodel was a flat, unlit-looking `color`-only material next to an otherwise-textured gunmetal barrel/body — fixed by giving it a `map` too (the same gunmetal texture, tighter tile repeat, tinted darker) rather than generating a whole separate asset for a small part.
- Reverified visually via scripted close-range and angled screenshots: the model now reads clearly as a blocky tactical soldier (legs/torso/arms/head/visor all distinguishable) at both close and mid range, and the crate blends into the environment instead of standing out.
- **Deliberately not done in this pass** (geometry/texture only, not full character work): no rigged skeleton/animation (arms and legs are static blocks, matching the original capsule's lack of animation — a bigger lift than this "fix what's missing/bad" pass asked for), no face/skin texture on the head block, no distinct male/female or per-loadout model variants.

## Post-pivot fixes and additions (round 3): weapon/prop textures + a critical fog-distance bug

Started as "make better textures for all the guns and everything that is missing" but turned up a much more serious bug along the way.

- **Weapon viewmodels rebuilt entirely.** There was previously one static box glued to the camera regardless of equipped weapon. `Scene3D` now has `buildGunModel(weaponClass)` — distinct procedural geometry per class (pistol/smg/rifle/sniper/melee), gunmetal-textured — and `rebuildViewmodel()`, called from the render loop whenever `activeWeaponId(localPlayer)` changes (buy a new gun, swap weapons), disposing the old group's geometry/materials first. Confirmed all five classes render as visually distinct and swap live.
- **Prop crates textured** (`material.crate`, a wood-with-metal-corners texture tiled per prop's box dimensions), replacing the flat-color boxes.
- **Player capsules textured carefully, not naively.** First attempt put the fabric texture straight on `MeshStandardMaterial.map` alongside the team `color` — Three.js multiplies map × color per-pixel, so the bright amber/teal identity color turned into a muddy brown. Fixed by moving the texture to `bumpMap` instead (adds surface relief, doesn't touch the color channel) and keeping `color` as a flat, undiluted, instantly-readable team color. Confirmed via screenshot before/after.
- **Critical bug found while testing the above, reported independently by the user as "we can't see or hear each other" in a real two-window session against the live deployment**: `scene.fog` was `THREE.Fog(0x05060a, 260, 1150)` — fully opaque (pure fog color, i.e. invisible) at 1150 units. Both maps' raider/warden spawns are **1760 units apart** in a straight, unobstructed corridor. Two players who just spawned and looked at each other — the single most obvious thing to try — saw nothing but black void, even though positions, inputs, and snapshots were syncing perfectly the whole time (verified: real two-context P2P session against both the dev server and the live Vercel URL showed correct ping/tick/snapshot-byte counters and zero console errors on both sides while they were each invisible to the other). This was a pure rendering-distance bug, not a networking bug, and would have hit *any* two players on either map regardless of connection quality. Fixed by extending fog to `(0x05060a, 300, 2500)`, comfortably past the longest sightline on either map; reverified the opponent is now visible both at close range and at the full 1760-unit spawn-to-spawn distance, and that the fog atmosphere still reads as intentional (dim/hazy at range, not a hard cutoff).
- End-to-end loop reverified after the fog fix with a live two-context session: visibility at spawn distance → close-range combat via real input (mouse click, not HP hacks) → kill registered → "Round Won / Eliminated" banner → round score incremented → kill money payout credited → round transitions to freeze/buy phase. This is the spawn→fight→money→buy→spawn loop the user asked to see working, confirmed live rather than assumed from the code.

## Post-pivot fixes and additions (round 2): real vertical aim + jumping

Reported by the user: "bullets go in front of the face not where the crosshair is looking." Root cause was DD-014 (below) — pitch was deliberately kept client-only and hitscan stayed a flat ray at `EYE_HEIGHT`, so looking up/down visually moved the crosshair but never changed where a shot actually landed or where the tracer was drawn. That's now fixed properly rather than patched around:

- **`pitch` now travels with every input** (`InputWire`'s 9th tuple field) — read only by the host, only at the instant a shot fires, to resolve real vertical aim. It's deliberately *not* persisted on `PlayerState` or broadcast in snapshots (no reconciliation needed for a value that's consumed once per shot).
- **`sim/combat.ts` gained `pitchedHeightAt`/`computeVerticalHit`**: given the existing horizontal (XZ) closest-approach distance to a target (unchanged — `circleHitTest` still does the 2D math it always did) plus the shooter's pitch, works out the actual world height the ray passes through at that point and whether it falls inside the target's hitbox (`HITBOX_MIN_Y`..`HITBOX_MAX_Y`, feet to just-above-head). Walls are still treated as full-height blockers (a 2D XZ raycast against wall segments, unchanged) — reasonable since walls (240 units) are much taller than the hitbox range and the maps are single-story.
- **Vertical position now overrides the hit zone**: aiming into the top/bottom slivers of the hitbox forces a head/leg zone outright (`classifyVerticalZone`), on top of the existing facing-relative horizontal zones (DD-008). This is what makes the fix *matter* for damage, not just for whether a shot connects at all — confirmed live: a flat shot at a same-eye-height target lands as an instant headshot (eye height sits naturally near the top of the hitbox for a flat trajectory), and the same shot pitched up ~74° over a flat-standing target correctly misses entirely.
- **Tracer/muzzle-flash visuals now use the same math** (`Effects.tracer`/`muzzleFlash`/`impact` signatures gained explicit height parameters) so what you *see* matches what actually happened, including through jumps (origin height includes the shooter's `jumpZ` at the moment of the event).
- **Jumping added**: `BUTTON_JUMP` (Space / a dedicated mobile button), simple gravity-integrated `jumpZ`/`jumpVel` on `PlayerState` (`sim/movement.ts`), single jump only while grounded (holding the button doesn't re-trigger mid-air). `jumpZ` is synced in `PlayerWire` (`jz`) so the remote view renders the other player's hop, though — unlike x/y/angle — it isn't run through the interpolation buffer, so remote jumps render at raw 30Hz rather than smoothly interpolated (a minor, deliberately-accepted cosmetic gap; jump arcs are fast and this doesn't affect hit detection, which is always server-authoritative regardless). Verified live: `jumpZ` rises to a clean peak and returns to exactly 0, matching the tuned gravity/impulse constants.
- **Fixed two independent mouse/movement inversion bugs** found in the same review pass (see the entry below).

## Post-pivot fixes and additions (round 1)

- **Fixed real mouse/movement inversion bugs.** Reported by the user immediately after the 3D pivot shipped. Two independent sign errors: (1) `DesktopControls`/`TouchControls` applied `yaw -= movementX * SENS` — moving the mouse right *decreased* yaw, turning the camera left instead of right. (2) The strafe (A/D) contribution to `moveX`/`moveY` had the wrong sign relative to the derived "true right" vector `(-sin(yaw), cos(yaw))`, so A and D were effectively swapped. Both fixed and verified with a scripted test: at yaw 0 (spawn), moving the mouse right by 200px now increases yaw (turns right, confirmed via the actual simulated angle, not just visually), and pressing D at yaw 0 now moves purely along `+y` (sim) with zero `x` drift, matching the true right vector exactly.
- **Added a one-time onboarding tutorial** (`ui/Tutorial.ts`) — four floating "blob" hint bubbles (money/economy, buy-phase/shop, round-win condition, TAB-for-scoreboard) positioned near their relevant HUD elements, each individually dismissible and auto-fading after 18s, gated by a `localStorage` flag so returning players in the same browser don't see it again once all four have been dismissed or expired.

## Phases 1–7 (original top-down build)

Kept below for history — the netcode, sim, rounds, economy, and mobile-input-scheme *logic* described here is still exactly what's running; only the rendering/camera/aim layer changed, per "The 3D pivot" above.

### Netcode (Phase 1)
Host-authoritative simulation, 30Hz tick, 60fps render. Client-side prediction + reconciliation (replay-from-ack on every snapshot, small corrections glide over 100ms, larger ones snap). Remote-player interpolation at a 100ms delay, frozen (never extrapolated) past 250ms. Trystero P2P: nostr signaling primary, BitTorrent-tracker fallback after 6s. Compact wire protocol — input packets are tuples, snapshot state uses short-keyed objects (see DD-007).

### World + vision (Phase 2, now superseded — see "The 3D pivot")
Two maps (`src/data/maps/depot.json`, `terrace.json`) as data, loaded through a tiny typed loader. Axis-aligned rect walls + props, resolved with circle-vs-rect collision in `sim/collision.ts`. ~~Fog of war: a 100° cone (700px) + 90px 360° near-radius... rendered as a GeometryMask~~ — this rendering approach no longer exists; the *map data* and *collision* it's describing are unchanged, but visibility is now handled by real 3D occlusion.

### Combat (Phase 3)
Hitscan weapons with fixed 30-value spray patterns, movement-scaled inaccuracy that recovers over ~0.4s, armor absorption (50%, degrades per hit), head/chest/leg zones classified relative to the *target's* facing (frontal 90° arc = head, rear 90° = legs, sides = chest — see DD-008), lag-compensated hit detection (rewinds the target to `hostTime − rewindDelay`, capped at 250ms, using the exact same `sim/interpolate.sampleAt` the render-side interpolation uses). Melee (Shard) is a short-range arc check with a backstab multiplier. Cosmetic effects (muzzle flash, tracer, impact billboard, hit-flash, screen shake) and procedural Web Audio (positional, with a lowpass "muffle" when occluded by a wall) all in `render/Effects.ts` / `audio/` — `Effects.ts` is now a Three.js implementation (the Phaser one it replaced is gone).

### Rounds + economy + buy menu (Phases 4–5)
Full freeze(12s)/live(95s)/roundend(4s)/matchend state machine in `sim/rounds.ts`, first-to-7 / best-of-13, side swap after round 6, escalating loss-bonus ladder, round-win/kill/plant/defuse payouts, $16000 cap, weapons reset every round but money carries over. Breach charge plant (raider, hold E in the site) / defuse (warden, hold E on the bomb, faster with a kit) with a +35s detonation timer. Full arsenal from the spec's weapon table plus armor/helmet/defuse-kit/flash/smoke/frag, all buyable through a DOM buy sheet (`ui/BuyMenu.ts`) that's also the mobile full-screen buy sheet. Flash blinds anyone looking at the landing point; smoke still occludes the hitscan raycast exactly like a wall (now also gets a translucent visual sphere — DD-017).

### Mobile (Phase 6, input scheme updated — see DD-015)
Touch devices get a virtual joystick (`ui/TouchControls.ts`) for movement (relative to camera facing) and a drag-to-look zone for the camera, plus a dedicated FIRE button and contextual reload/use/grenade/weapon-swap/buy buttons. Landscape-only gate in portrait. Same `Controls` interface (`render/controls.ts`) is implemented by both `DesktopControls` and `TouchControls`, so `Scene3D` doesn't know or care which one is active.

### Polish (Phase 7)
Nickname capture (persisted in `localStorage`, exchanged over a one-time "hello" P2P message), map choice at Create Match, share-link copy + native share-sheet button when `navigator.share` exists, round-end banner, match-end results screen with a rematch button (host resets world/match state, keeping the WebRTC connection and the monotonic snapshot tick counter alive — see DD-009), a Tab-held scoreboard, and disconnect handling (3s "reconnecting" grace, then a clean "opponent disconnected" / "host left" screen — see DD-010 for what's *not* attempted here).

## Director Decisions — original top-down build (history)

*(DD-001 through DD-006 are from Phase 1 — see git history if needed; they covered the nostr/torrent fallback strategy, Trystero's lack of an unreliable-channel option, the fixed 2-slot player model, host self-simulation, sending velocity in the snapshot for correct reconciliation replay, and the `window.__breach*` dev-only debug hook.)*

- **DD-007**: Switched the snapshot wire format from positional tuples (Phase 1's `PlayerWire`) to short-keyed objects once combat/rounds/economy pushed the field count past ~10. Positional tuples become error-prone to maintain correctly at that size — a single index shift is a silent, hard-to-spot bug — and the extra bytes are irrelevant at 1v1 scale on a WebRTC data channel. Input packets stayed tuples since they're small, fixed-shape, and sent at render-frame frequency.
- **DD-008**: Hit-zone classification (head/chest/leg) is done via angular arcs around the target's hitbox circle *relative to the target's own facing* (frontal 90° = head, rear 90° = legs, the two 90° side arcs = chest) rather than a literal 3D head-height model. Written when this was a 2D top-down game with no vertical axis; still exactly how it works post-pivot too, since hitscan still resolves in the flat XZ plane (DD-014).
- **DD-009**: Rematch resets `world`/`match` state but deliberately preserves the snapshot tick counter (doesn't reset it to 0) and the connection. Resetting tick to 0 would make the client's `tick <= lastAckedTick` staleness check permanently reject every future snapshot, silently freezing the client. Preserving it costs nothing and avoids that whole class of bug.
- **DD-010**: Disconnect handling implements the spec's literal ask (3s "Reconnecting…" grace, then a clean end screen; "Host left" with no migration attempt if the host is the one who's gone) but does **not** implement full peer-rejoin matching. The grace period still does real work: it distinguishes a transient ICE hiccup (which can self-heal without ever firing `onPeerLeave` again) from a genuine departure.
- **DD-011**: Grenades (flash/smoke/frag) resolve at an instantly-computed raycast landing point rather than simulating a physical lobbed throw with travel time and gravity arc.
- **DD-012**: Map selection happens once at Create Match (a two-option radio choice: Depot or Terrace); there's no in-match map voting/veto system.
